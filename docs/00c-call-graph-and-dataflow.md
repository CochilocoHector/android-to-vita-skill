# 00c · 调用链与数据流

## 1. 从现象选入口

| 现象 | 可能的入口 |
|---|---|
| 黑屏/花屏 | 渲染循环、纹理加载、设备能力判断全局 |
| UI 空白 | GUI 管理器 draw/load、SWF 资源加载、名字匹配 |
| 静音 | JNI 播放方法、音频引擎、资源打开 |
| 崩溃 | 日志停点、dump PC、最近一次外部调用 |

**原则**：入口要能通过日志/字符串/导出符号定位，不要从"最像的函数名"开始。

## 2. 向下追一层：看它调用谁

```bash
python3 tools/arm_xrefs.py libGame.so 0x13c584
```

或直接看反汇编里的 `bl`，把目标还原成符号：

```bash
python3 tools/elf_info.py libGame.so | grep -i "plt\|strstr\|memcmp"
```

产出：`draw() → RenderFX::Render() → gameswf` 这样的骨架。

## 3. 向上追一层：谁调用它

```bash
python3 tools/arm_xrefs.py libGame.so 0x13ba58
```

- 直接 `bl` 命中 → 调用者明确
- 无命中 → 可能经函数指针/vtable 调用，需看运行时（日志打印 `caller=+0x...`）

## 4. 结构体字段推断

不要凭字段偏移猜语义。用三个来源交叉：

1. **写入点**：谁 `str` 到这个偏移，值是常量还是函数返回
2. **读取点**：谁 `ldr` 这个偏移，用在什么比较/调用里
3. **相关函数**：同名结构体的构造函数/初始化函数

示例推理：

```
+0x10 被 load 当作 const char* 传给 strstr → 名字指针
+0x14 被 str 写入计数器返回值，又被读作 id → 纹理 id
```

## 5. 门控（gate）分析

很多"没生效"的问题是被前置条件挡住。分析方法：

```
GATE1: 条件 A 不满足 → 跳过
GATE2: 条件 B 不满足 → 跳过
LOAD:  真正执行
```

**只观测，不调用**：在两个门控入口挂日志，按调用顺序判断：

```
GATE1 → GATE2 → LOAD     两道都过
GATE1 → 下一个 GATE1     门控一失败（门控二没被调用）
GATE1 → GATE2 → 下一个   门控二失败
```

若通过函数名/参数无法判断"结果"，不要为了日志额外调用它；
用后续是否发生 LOAD/其它调用来反推。

## 6. 状态机分析

典型：播放器数组 + 状态数组。

```smali
a[id] == 7  → 需要重新加载
a[id] in {5,6,8,9} → 可以播放
start 后 a[id] = 6
```

还原步骤：

1. 列出所有对状态数组的写入常量
2. 列出所有比较分支
3. 画出状态迁移图
4. 找出"重复调用时会发生什么"（这是移植最容易错的地方）

## 7. 数据流：资源如何被打开

```
调用方 → 文件名生成 → open/mmap → 解析头 → 上传/解码
```

- 文件名生成：拼字符串（`"./%s"`、`"000"+id`），把所有分支写完
- 文件打开：hook `open`/`fopen` 记录路径与返回值
- 解析头：用 `tools/btex_info.py` 对照
