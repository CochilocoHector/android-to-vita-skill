# 00 · 静态逆向工程总流程

> 本 Skill 的核心：**先把原版行为从二进制里读出来，再写兼容实现**。
> 静态分析与运行验证互补，任何一方单独都不足以称为"已确认"。

## 1. 五步流程

```
① 收集事实
  现象、日志、dump、资源头、APK 结构、依赖库
        ↓
② 静态还原
  DEX/ARM/调用链/数据流 → 原版函数、参数、状态、生命周期
        ↓
③ 写兼容规格
  一张表：接口 / 参数 / 返回值 / 状态变化 / 资源映射
        ↓
④ 最小实现
  只实现规格里的那一个闭环，其他先不动
        ↓
⑤ 验证
  运行日志（调用是否发生、参数是否正确）+ 实机测试（现象是否消失）
```

## 2. 每个问题必须回答的 9 问

| # | 问题 | 回答不了时 |
|---|---|---|
| 1 | 现象是什么？ | 回到日志/截图，量化现象 |
| 2 | 原版由哪个函数/模块负责？ | 用符号、字符串、xref 缩小范围 |
| 3 | 能否用 DEX/ELF/资源定位？ | 换入口：资源名、错误串、全局变量 |
| 4 | 原版调用链是什么？ | 从入口向上/向下各追一层 |
| 5 | 关键参数、分支、状态是什么？ | 列出所有 early return 与比较 |
| 6 | 兼容实现与原版差在哪？ | 写差异表，逐条对照 |
| 7 | 哪些结论已被静态证实？ | 标注地址与指令 |
| 8 | 哪些还需运行验证？ | 设计最小日志实验 |
| 9 | 最小修复是什么？ | 只改差异表中的一行 |

**停止规则**：静态分析无法继续时，明确写出"缺什么证据"，
设计一个最小动态实验（一个探针、一次运行），而不是继续猜。

## 3. 证据记录格式

每个结论按下面格式落到项目知识库：

```markdown
### <主题>
- 事实：一句话
- 来源：[ASM]/[DEX]/[BYTES]/[LOG]/[TEST]
- 证据：
  地址 0x... 指令 ...
  或 smali ...
  或 日志原文 ...
- 状态：✅已确认 / ◐推测 / ☐待验证
- 影响：会导致什么行为
```

## 5. 判断标准：什么时候算"静态已确认"

一条结论可以标 ✅ 的条件（满足其一）：

- 反汇编中看到明确分支/调用/常量，且能解释现象
- DEX 中看到方法签名、控制流与常量
- 数据字节与代码逻辑互相印证（如长度字段与偏移表 149/149 吻合）

以下只能标 ◐ 或 ☐：

- "这个名字看起来像是……"
- "函数名叫 loadXxx 所以应该……"
- 只有单一证据且未复现

## 6. 常见误区

| 误区 | 后果 | 纠正 |
|---|---|---|
| 用函数名推断用途 | 误判入口 | 看调用者与被调用者 |
| 只看一处证据 | 结论不可靠 | 至少两条独立证据 |
| 把静态推断当运行事实 | 修复方向错 | 用日志验证调用是否发生 |
| 忽略 PC 相对寻址 | 读到错误全局变量 | 计算字面量地址要 `addr+4` 对齐 |
| 忽略 Thumb 位 | 跳到 ARM 状态崩溃 | 跳转地址 `| 1` |

## 7. 与运行验证的分工

| 静态分析能确定 | 只有运行能确定 |
|---|---|
| 函数存在与调用关系 | 这次运行是否真的走到 |
| 参数个数与类型 | 参数的实际值 |
| 分支条件与常量 | 走了哪个分支 |
| 资源映射规则 | 文件是否真的存在/可读 |
| 播放器实例模型 | 同时有几个实例在跑 |
